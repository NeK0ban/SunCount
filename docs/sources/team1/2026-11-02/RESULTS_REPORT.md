# SunCount — отчёт команды №1 по многолетним данным PVGIS

**Дата подготовки: 02.11.2026.**  
**Статус: расчётный энергетический пакет готов к передаче команде №2, независимая валидация по бытовым измерениям пока не проведена.**

## 1. Цель и итог

Проект «Окупаемость домашней солнечной электростанции» исследует, как бытовой почасовой профиль и тарифы влияют на экономику СЭС. Команда 1 отвечает за потребление, солнечную выработку и энергобалансы. Команда 2 отвечает за тарифы, цену выкупа, инвестиции, окупаемость и веб-калькулятор.

**Главный итог:** вместо демонстрационной 2023 солнечной базы применены предоставленные два PVGIS JSON за 2005–2023 гг. Рассчитаны все 24 годовые и 288 помесячных записи; 8 профилей потребления и 6 рядов солнечной генерации имеют по 8760 часов.

## 2. Проверенный источник данных

- Исходные файлы: `krasnodar_2005_2023.json` и `maykop_2005_2023.json` из пользовательского архива `data/pvgis_raw/pvgis_2005_2023_original_upload.zip`; у каждого **166 536** записей (19 календарных лет с четырьмя високосными днями). Проверены метаданные, непрерывность временной сетки, отсутствие отрицательной генерации, контрольные суммы SHA256. Проверена **структура**, а не независимая подлинность источника/его сервера.
- **Краснодар**: `45.0355, 38.9753`; **Майкоп**: `44.6098, 40.1007`.
- `PVGIS-SARAH3` + `ERA5`, 2005–2023, модуль c-Si, 1 кВт, наклон 30°, PVGIS aspect=0° (строго юг), потери 14%, горизонт учтён, free-standing.
- Солнечная энергия на каждом часе = `P[W]/1000 × 1 час`, без аккумулятора. Данные PVGIS — **модель выработки**, а не показания домашнего электросчётчика.

## 3. Как построен типичный год

Время источника UTC с минутой `:10` переведено к фиксированному UTC+3. Из многолетнего массива сформирован типичный год: для каждого сочетания **месяц, число, час** вычислена арифметическая средняя выработка по 2005–2023 гг. 29 февраля исключено, итоговый календарь — условный невисокосный 2023 год с 8760 часов. У 8757 локальных часов есть 19 исходных значений, у трёх часов 1 января в начале суток — 18: крайний 2004 год отсутствует в выгрузке; солнечная выработка в эти ночные часы нулевая.

Это 19-летний средний почасовой сценарий, а **не метеопрогноз будущих 25 лет и не наблюдённый конкретный год**. В данном расчёте 3/5/10 кВт масштабируются линейно от 1 кВт. Для экономической оценки на срок службы 25 лет второй команде остаётся учесть деградацию панелей, тарифы и тарифные ступени.

## 6. Домохозяйства и энергетический баланс

Четыре обязательных профиля × два города: `day_absent`, `home_all_day`, `ac`, `el_heating`. Почасовые нагрузки являются **сценариями**, воспроизводимо распределёнными из прежних месячных итогов (`data/reference/monthly_load_2023.csv`); они **не являются измерениями конкретных семей**. Учитываются типичные дневные пики, дневное присутствие, сезонность кондиционирования и отопления, выходные дни. Для сценария «Свои данные» функции `build_profile` и `simulate` возвращают 8760 часов и 12 `MonthlyMetrics` для тарифа по месяцу.

В каждом часе:

- `self_kwh = min(load_kwh, gen_kwh)`;
- `import_kwh = max(load_kwh - gen_kwh, 0)`;
- `export_kwh = max(gen_kwh - load_kwh, 0)`.

День — 07:00–22:59, ночь — 23:00–06:59 (UTC+3). По каждому часу и агрегату выполняются равенства: **потребление = самопотребление + импорт** и **генерация = самопотребление + экспорт**. Ночная доля самопотребления отдельно в формате v1.0 не выделена; согласование v1.1 необходимо только при потребности команды №2.

## 7. Проверка гипотезы при равном потреблении

Оба профиля `day_absent` и `home_all_day` нормированы на **3500 кВт·ч за год** в каждом городе, при сохранении исходной формы почасовой нагрузки. Проверяется строго `self_share = self_kwh / gen_kwh × 100%`. При равном годовом расходе отношение `coverage` между портретами совпадает с отношением `self_share` в рамках данной пары.

| Город | СЭС, кВт | self_share: никого днём, % | self_share: кто-то дома, % | Во сколько раз | ≥1,5? |
|---|---:|---:|---:|---:|:---:|
| Краснодар | 3 | 27.09 | 43.97 | **1.6230** | Да |
| Краснодар | 5 | 18.03 | 28.35 | **1.5723** | Да |
| Краснодар | 10 | 9.97 | 14.96 | **1.5002** | Да |
| Майкоп | 3 | 27.37 | 44.46 | **1.6244** | Да |
| Майкоп | 5 | 18.21 | 28.64 | **1.5729** | Да |
| Майкоп | 10 | 10.08 | 15.11 | **1.4995** | Нет |

**Вывод:** в сценарной модели гипотеза подтверждается для СЭС 3 и 5 кВт в обоих городах и едва выполняется при 10 кВт для Краснодара (1,50017), но немного не выполняется для Майкопа (1,49953). Это практически пороговый результат, чувствительный к допущениям модели и не доказывает универсальную закономерность для реальных домохозяйств. Нельзя сообщать, что гипотеза подтверждена для всех рассмотренных случаев.

## 8. Автоматический контроль и формат файлов

- 24 годовые записи в `results/energy_metrics.csv`.
- 288 помесячных записей в `results/energy_metrics_monthly.csv`.
- 8 файлов по 8760 строк в `data/hourly_profiles/` и 6 файлов по 8760 строк в `data/hourly_solar/`.
- Коды, единицы и названия полей соответствуют восстановленному формату v1.0. `src/econ/exchange.py` — локальный совместимый аналог класса команды №2, не оригинальная реализация.
- Источники и контрольные SHA256 лежат в `data/solar_reference/*.meta.json`; полный первоначальный ZIP лежит в `data/pvgis_raw/`.
- Тесты и контрольное сравнение месячных/годовых сумм, балансов и исходного архива входят в поставку.

## 9. Что ещё нужно для полностью закрытого задания

**Для команды №2:** проверить несовпадение климатических контрольных цифр и прислать оригиналы `docs/exchange_format.md` и `src/econ/exchange.py` для проверки интеграции. **Для научной валидации:** предоставить анонимизированные наблюдения 3–5 семей за 1–2 недели; численную точность сценарных профилей до этого оценивать нельзя. **Для экономики:** тарифы, правила выкупа и 25-летняя финансовая модель — ответственность команды №2.

## 10. Воспроизведение

```bash
python -m pip install -r requirements.txt
python -m scripts.import_uploaded_pvgis
python -m scripts.generate_outputs --mode verified
python -m unittest discover -s tests -v
```

Запросить PVGIS повторно не нужно — оригинальный ZIP находится в поставке. При смене наклона, азимута, местности или модели панелей нужен новый исходный файл и пересчёт.
